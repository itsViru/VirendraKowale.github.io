ISO 15118-2 & -20 charging communication: validation bench

Method, standards and test strategy. Topology, addressing and vendor details deliberately omitted.

01 · The goal, and what I built

The goal: develop, create and run test cases for the new ISO 15118-20 charging protocol on our existing charger and EV-simulator hardware test setup, validating ISO 15118-2 alongside as a baseline. To do that reliably, I built a validation bench in two stages: software-in-the-loop first, with station and vehicle both simulated entirely in software, then hardware-in-the-loop against a physical charging station and a physical EV-simulator board joined by a real CCS/PLC link.

The protocol stack is identical in both stages. Only the driver layer beneath it changes, which is what makes a HiL-only failure environmental by construction.

04 · How I built the bench

I built it bottom-up, proving each layer before adding the next: software first, then hardware, then secure transport.

  • 1 · Software (SiL). Installed and ran EVerest on my own Ubuntu Linux machine with a simulated charger and a simulated EV, and validated both ISO 15118-2 and -20 end to end, entirely in software, no hardware.
  • 2 · Hardware (HiL). Connected a real charging station and a real EV-simulator board by adapting the EVerest YAML configuration and the relevant driver modules for each side, joining them over a dedicated virtual network segment. When the EV first couldn't locate the station over the network, I raised the SDP (SECC discovery) retry count to 10, which let discovery complete reliably and brought the whole setup up.
  • 3 · Backend, separated. Ran the OCPP backend from its open-source repository on the same machine but on a separate network interface, so charging-protocol and backend traffic never share a Layer-2 segment, so every capture stays single-protocol.
  • 4 · Secure transport. With the plumbing in place, I brought up the TLS connection between EV and charger. ISO 15118-20 runs over TLS 1.3, whose ephemeral keys mean a captured session cannot be decrypted from a static private key. So I had EVerest export the per-session TLS secrets as a key-log, then pointed Wireshark at that file in its TLS settings (Preferences → Protocols → TLS, key-log file), which turns the otherwise-opaque application data back into readable ISO 15118-20 messages. Lab-only, on the test bench. Without it, everything above the handshake is a black box.

Underneath, the rig has four roles: the station is the system under test; the EVerest EVCC and the EV board are stimulators; the per-segment captures and logs are observers; the per-step response code is the referee. Control Pilot states A/B/C are driven on command, so every scenario is deterministic and repeatable. Once the full ISO 15118-20 session ran clean, I drove test scenarios through EVerest's MQTT external-control API: starting a charging session, interrupting it mid-flow, and injecting timing delays to slow the sequence. That let me actively exercise the running setup on demand across both -2 and -20.

One finding from driving those scenarios: after pausing a running session through the MQTT control API, I could not resume that same session and had to start a fresh one. ISO 15118 itself permits resuming a paused session under the same session ID, so this was a limitation of the EVerest control interface on my bench, not of the protocol. A useful reminder that a tool's session handling does not always match what the spec allows.

05 · The defect, worked

Symptom. Authorization step fails. The station logs a digest mismatch, pointing at integrity.
Localize. The TCP teardown landed immediately after the request, naming the failing step before any decryption.
Hypothesis. Decrypted, the signature was structurally sound. It failed identically every run. Deterministic means configuration, not computation.
Verify. openssl showed the vehicle leaf chained to a different root than the one in the station's trust store.
Fix. Regenerate the vehicle PKI under the shared root; install that root into the station's trust store.
Regress. Full sequence re-run green on both protocol versions, proof the fix broke nothing else.

The point: a certificate can be perfectly valid and still untrusted. Validity is mathematics; trust is configuration. The error message named the wrong check.

An experienced colleague pointed me toward the trust store as the likely cause; from there the confirmation with openssl and the logs, and the fix under a shared root, were mine to carry out.

06 · What passed, and how I knew

  • ISO 15118-2: 10 steps green.
  • ISO 15118-20: 13 steps green. No FAILED_* codes end to end.
  • Both versions on one bench, a comparative baseline.
  • Binary oracles: response code OK on every step · SLAC reaching matched · keylog line count confirming TLS 1.3 · openssl verify returning OK.
  • Forbidden paths confirmed closed: neither segment's capture contains the other's protocol.

07 · What's next

  • The automated regression suite is designed, not built. The attachment points exist: the MQTT control API as a test driver, the per-step response codes as assertions, Pytest and CI to run and gate it.
  • First check I would add: a pre-session openssl verify on both chains against both trust stores, so a trust mismatch fails as a missing entry criterion rather than as a confusing mid-session error.
  • Once built, the automation replaces the manual bring-up, capture and verification repeated for every scenario, turning a hand-driven session into a scripted run; any time saving stays unquantified until measured. My code edits were Python; C/C++ at reading level.
