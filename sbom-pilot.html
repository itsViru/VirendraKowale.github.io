Firmware vulnerability tracking: an SBOM and Dependency-Track pilot

Method, data sources and triage logic. Product, component and finding details deliberately omitted.

01 · The goal, and what I set up

The goal: know, continuously and with an audit trail, which publicly known vulnerabilities could affect the software inside a charger firmware. In a 20-hour pilot I set up Dependency-Track and connected a bridge tool that repairs missing component identifiers and adds EU vulnerability data, so the firmware's software bill of materials (SBOM, 72 components) was checked against three public sources on a schedule.

The pilot answered one question: does the chain work end to end on real firmware? It did. This page describes the method and what I learned; the follow-up planning is internal.

04 · The identifier gap, worked

Symptom. The first upload looked healthy, but a share of the components came back with no findings at all. Not "clean": never checked.
Localize. Those components had no machine-readable identifier (CPE), so the matcher had nothing to look up and skipped them without a warning.
Hypothesis. The build system and the vulnerability catalogue name the same software differently, so identifiers are missing or do not line up.
Verify. Three search passes against NVD. A plain keyword search missed one product because NVD spells it differently, so the final pass read identifiers straight from NVD's own CVE records.
Fix. Added identifiers where a correct one exists. Deliberately left one component alone, because the only matching identifier belonged to a different product.
Classify. Sorted the remaining 20 into four classes, each with a written reason, so nothing is silently unchecked.

The point: a component without an identifier is not safe, it is unchecked. And a wrong identifier is worse than none, because it produces false findings that cost trust. The cleaner long-term fix is to set the identifier fields in the Buildroot package files, so every SBOM is correct at the source.

05 · What the pilot shows, and how I know

  • All 72 components accounted for: 52 checked automatically, 20 explained.
  • The three-source check ran end to end, every 6 hours and on every upload.
  • EU data was merged into the findings inside Dependency-Track, next to the NVD match.
  • Results were available as JSON for whatever comes next.
  • Triage stays human. A score is not a verdict: a flaw can carry a top severity rating and still not apply, for example when it only affects another operating system or a feature that is not built in. Each decision is recorded with its reason.
  • A raw count is not a result. In embedded Linux firmware, most candidate findings typically come from the kernel, many for drivers that are not compiled in. Filtering by kernel configuration is the standard way to cut that noise.
  • Information, not decisions. Tracking shows what may apply. Whether and when to update a component stays with the product team.

One trade-off accepted on purpose: limiting the check to three authoritative sources means no automatic upgrade targets and more findings for manual review. Part of that automation can be restored later without adding another vulnerability source.

06 · What I took from it

  • An SBOM is only as good as its identifiers. Count the components that were never checked before you trust the findings.
  • Few sources you can defend beat many you can't. Three authoritative, free sources keep every finding explainable to an auditor.
  • Fix data at the source. Identifiers belong in the build system's package definitions, not in a list of manual overrides.
  • Keep the human step visible. The tool flags; a person decides, and writes down why.
